## 1. 휠 모드 분리 (요청 1·4)

원인은 두 가지가 겹쳐 있었고, 둘 다 실제 결함이었습니다.

**① 임계값이 조작계를 구분하지 못했다.** v2.6.0은 누적 임계값 하나(100px)만 봤습니다.
윈도우 마우스 휠 한 칸은 약 53px이라 **한 줄 넘기는 데 두 번** 굴려야 했고,
값을 낮추면 이번엔 트랙패드의 미세 델타가 줄을 마구 넘겼습니다.
지금은 `40px` 이상이면 "마우스 한 칸"으로 보고 **즉시 한 스텝**, 그 미만은 트랙패드로 보고
누적합니다(`lib/utils/wheel_step_accumulator.dart`).

**② 모드를 바꿔도 이전 모드의 잔여 델타가 남았다.** Ctrl을 놓는 순간 남아 있던
누적값이 줄 이동으로 새어 나갔습니다. 모드 전환 시 **모든 누적기를 초기화**합니다.

```
휠        → 줄 이동
Ctrl + 휠 → 글자 크기
Alt  + 휠 → 키(피치)
```
`wheelModeFor()`가 하나만 고르므로 구조적으로 동시 적용이 불가능합니다.
메인 창과 전체화면이 같은 `PrompterWheelScope`를 씁니다.

## 2. 현재 줄 강조 (요청 2)

색 하나에 기대지 않고 **네 가지를 겹칩니다** — 큰 화살표(글자 크기의 1.0배),
아래 밑줄(4px), 옅은 배경, 오렌지 글자. 스크린 리더에는 `Semantics(selected:)`로 알립니다.

강조가 안 보이던 진짜 원인도 함께 고쳤습니다: 글자 크기가 바뀌면 줄 높이가 달라져
현재 줄이 화면 밖으로 밀려나는데, `currentIndex`가 그대로면 다시 따라가지 않았습니다.
이제 **크기·줄수 변화도 재추적 조건**에 넣었습니다.

## 3. Home / End (요청 5)

`PrompterKeyboardScope`에 `Home`=트림 시작, `End`=트림 끝. `seek()`가 트림·길이로
클램프하므로 큰 값을 넘겨도 안전합니다.

## 4. Alt+휠 키 조절 (요청 6 전반)

키 변경은 **곡 전체를 다시 인코딩**하는 오프라인 작업이라 한 칸마다 렌더하면
같은 곡을 몇 번이고 다시 굽게 됩니다. 그래서 나눴습니다.

- **화면은 즉시** — 굴리는 값이 화면 한가운데 큰 글씨로(`+1키` / `-2키`) 뜨고,
  아래에 옮겨진 조성(`A♭` → `G`)이 함께 보입니다.
- **오디오는 손을 멈춘 뒤 한 번** — 550ms 디바운스 후 적용하며,
  `keepPosition`으로 **부르던 자리에서 이어집니다**(처음으로 돌아가지 않음).

## 5. 곡 조성 자동 감지 (요청 6 후반)

ffmpeg에는 크로마·조성 필터가 없어 직접 만들었습니다. 12반음마다 여러 옥타브의
대역만 남겨(`bandpass`) 합친 뒤(`amix`) 전체 에너지를 재고(`astats`),
Krumhansl–Kessler 프로파일 24가지(장·단 × 12)와 상관을 재 가장 잘 맞는 것을 고릅니다.

### 실측으로 정한 것들

같은 곡의 세 파일(원곡 / MR / MR −2키, 각 247.8초)로 검증했습니다.

| 파일 | 판정 | 상관 |
|---|---|---|
| MR | **A♭** | 0.845 |
| MR −2키 | **F♯** | 0.856 |
| 원곡(보컬 포함) | E♭ | 0.870 |

- **MR과 −2키가 정확히 2반음 차**로 나왔고, 필터 설정 네 가지 모두에서 같았습니다.
- 반면 **보컬이 살아 있는 원곡은 딸림음 E♭로 끌렸습니다.** 멜로디가 상관을 흔드는
  고전적인 으뜸음/딸림음 혼동입니다. → **분석은 MR 슬롯에서만** 합니다
  (키조절 기준이 MR인 것과 같은 규약).
- `bandpass`는 2차 biquad라 한 번만 걸면 저역이 열두 대역 전부로 샙니다.
  **3단으로 겹치니** 크로마 대비가 0.40 → 0.67로 넓어져 그대로 채택했습니다.
- 곡 전체가 아니라 **20% 지점부터 60초만** 표본으로 씁니다. 12패스 합쳐 약 5초이고,
  결과는 `data/cache/keys/`에 캐시되며 반주가 바뀌면 함께 버려집니다.

### 상관계수는 정답을 보증하지 않는다

위 표에서 **틀린 E♭이 0.870으로 가장 높았습니다.** 상관은 쓰레기 입력을 거르는 데는
쓸모가 있어도 정답과 오답을 가르지는 못합니다. 그래서 감지값은 **제안**으로만 다루고,
곡 수정 창에서 언제든 고쳐 쓸 수 있게 했습니다(`C`, `Am`, `F♯m`, `Bb` 등 이명동음 포함).
읽을 수 없는 표기는 조용히 버리지 않고 그 자리에서 알립니다.

### 표시

화면에는 **지금 들리는 조성**을 보여 줍니다 = 곡 조성 + 파일에 구워진 키 + 사용자가 민 키.
전체화면 상단 바와 메인 창 키 줄에 배지로 뜹니다.

실제 앱에서 확인한 결과:

```
musicalKey = A♭
  slot 1  원곡     baked=+0  -> A♭
  slot 2  MR      baked=+0  -> A♭
  slot 3  MR -2키  baked=-2  -> F♯
```

## 6. 덤으로 고친 것 — 재생 길이가 항상 0이던 버그

조성 감지를 붙이다가 발견했습니다. `prepareAudioForSelection`이 반주를 물린 **뒤에**
길이를 0으로 초기화하는데, 그 사이 네이티브에서 도착한 `onDurationChanged` 값을
**도로 덮어써서** 길이가 영영 0에 머물렀습니다.

영향 범위가 작지 않습니다 — 진행바 총 시간, 방금 넣은 **End 키**, 싱크 가사가 없는 곡의
줄 클릭·휠 이동(추정 위치 계산)이 전부 죽어 있었습니다.

초기화를 **준비 전으로** 옮겼습니다. 실제 앱에서 `durationMs = 247849`로 확인했고
(ffprobe 실측 247.8초와 일치), 회귀 테스트를 추가했습니다.

`a3c41c3`부터 있던 기존 버그이며 이번 변경으로 생긴 것이 아닙니다.

## 데이터 정정 1건

"넌 언제나" 슬롯 3(`MR -2키`)의 `bakedSemitones`가 `0`으로 저장돼 있었습니다.
지난 세션에 파이프라인을 손으로 돌려 등록한 곡이라 이 필드가 채워지지 않았고,
그대로 두면 조성이 A♭으로 잘못 표시됩니다. `-2`로 바로잡았습니다.
원본은 `data/songs.json.bak-v2.7.0`에 남겨 두었습니다.

같은 상황을 앱에서 고칠 수 있도록 **곡 수정 창에 '구운 키(반음)' 칸**을 추가했습니다.
표시 전용이며 재생에는 쓰지 않습니다(파일에 이미 반영돼 있으므로 이중 적용 방지).

## 확인하지 못한 것

메인 창 하단의 **조성 배지와 EQ 미터는 눈으로 확인하지 못했습니다.** 이번 세션의
화면이 1280×720에 200% 배율이라 하단 바가 렌더 영역 밖으로 밀려나 캡처가 되지
않았습니다. 대신 값이 맞는지는 제어 API로 확인했고(위 슬롯별 표), 위젯 배선은
컴파일·테스트로만 검증한 상태입니다. **실제 화면에서 배지 위치와 크기는 한 번
봐 주시면 좋겠습니다.**

현재 줄 강조(화살표+밑줄+배경+오렌지)는 캡처로 확인했습니다.
